# YOLOv8 + TensorRT 部署（P3 项目②）

从 `yolov8n.pt` 到 C++ 推理服务：CUDA 前后处理、INT8 量化、精度/性能全链路测量。

**一句话结论**：YOLOv8n 在这张卡上 **FP16 是最优解**（1.33× 加速，精度损失 1e-3，95%CI ±5.9%）；
INT8 **精度可以做到 1.76 pt 掉点、但性能反而比 FP16 慢 7.7%**，因为模型不是算力受限。

> **口径提示**：上面的 1.76 pt 是 **128 张（coco128）** 上的掉点。
> **COCO val2017 全量（5000 张、pycocotools 官方协议）实测是 −1.27 pt**，见 **附录 A**。
> 两套口径不可混用；**对外引用请用附录 A 的数字**。

## 1. 快速开始

```bash
# 导出 ONNX（首次）
~/.venvs/torch/bin/python scripts/export_yolo.py

# 建 engine（约 60 秒）
./build/bin/yolov8_demo --onnx models/yolov8n.onnx \
    --save-engine models/yolov8n.engine --image models/bus.ppm

# 推理
./build/bin/yolov8_demo --engine models/yolov8n.engine --image models/bus.ppm

# 全部功能
./build/bin/yolov8_demo --engine models/yolov8n.engine --image models/bus.ppm \
    --bench-nms --streams 4            # NMS 交叉点 + 多流并发 + 显存账本
./build/bin/yolov8_demo --engine A.engine --engine2 B.engine --image models/bus.ppm
                                       # 交错对比两个引擎（消除时钟漂移）
```

| `--gpu-nms` | 用 GPU 版 NMS（默认 CPU，见 §9.1） |

| `--dump-input/--dump-output` | 导出张量，供和 PyTorch 对齐 |
| `--conf/--iou/--iters` | 阈值与重复次数 |

## 2. 模型结构：8400 从哪来

```
backbone → P3 80×80 → P4 40×40 → P5 20×20
              ↓  neck（PAN：上采样 + concat 反复融合）
         三个尺度各一个 detect head
              ↓  cat + reshape
        [1, 84, 8400]
```

```
8400 = 80² + 40² + 20² = 6400 + 1600 + 400     （三个尺度的网格总数）
84   = 4（cx,cy,w,h） + 80（COCO 类别分数）
```

**三个必须记住的点**（写错都不会报错，只会输出垃圾）：

| 坑 | 正确做法 | 写错的后果 |
|---|---|---|
| **通道在前** | `index(c,i) = c*8400 + i` | 写成 `i*84+c` → 数值全错，程序照跑 |
| **已 sigmoid** | 直接用 | 再做一次 → 分数全挤到 0.5–0.7 |
| **坐标已是像素** | 直接用 | 再乘 stride → 框放大 8/16/32 倍 |
| **letterbox 空间** | 反算 `(x-pad)/scale` | 不做 → 框整体偏移并缩小 |

## 4. 精度验证（四层）

| 层 | 比什么 | 实测 |
|---|---|---|
| ① **后处理语义** | 我们的 decode+NMS vs **ultralytics.non_max_suppression** | **5/5 匹配，坐标差 0.00 px** |
| ② **引擎等价性** | TRT vs PyTorch（**同一份输入**） | **相对 1.868e-06** |
| ③ 精度压缩 | TF32 / FP16 / INT8 vs FP32 | 见 §5 |
| ④ 业务指标 | mAP@0.5 | 见 §5 |
| （辅助）实现一致性 | CPU NMS vs GPU NMS | 逐位相同（**但这只是回归守卫**） |

### ① 为什么必须和 ultralytics 比

**CPU NMS 和 GPU NMS 的 A/B 只能证明"两个实现一致"（自证），证明不了"语义对不对"。**
两个实现出自同一个心智模型（同样的逐类抑制、同样的 `IoU > 阈值`、同样的 argmax 选类），
**语义错了会一起错，A/B 永远通过**。

```bash
./build/bin/yolov8_demo --engine models/yolov8n.engine --image models/bus.ppm \
    --dump-output dump/out.bin --dump-dets dump/dets.txt
python scripts/verify_nms.py --raw dump/out.bin --dets dump/dets.txt
```

**两级对比**：

| 级别 | 输入 | 回答什么 |
|---|---|---|
| 语义级 | 只用 `out.bin`（raw 输出） | **NMS 的定义对不对**（逐类/阈值/IoU/贪心/选类） |
| 实现级 | 再加 `dets.txt`（C++ 的最终框） | **我的 C++ 实现对不对** |

**实测结果（bus.jpg）**：

```
[① 语义级]  匹配 5 对，漏检 0，多检 0
            最小 IoU = 0.972   （bus 那框：分数差 0.0000，位置差 5.25 px）
[② 实现级]  匹配 5 对，漏检 0，多检 0
            最小 IoU = 1.000   （C++ 真实输出，逐框完全相等）
```

**判据用 IoU（`最小 IoU ≥ 0.90`），不用像素距离**：

> **① 里那 5.25 px 不是 bug**。NMS 遇到两个"近重复候选"（分数差 0.0000、IoU 0.972）时
> 只留一个，**留哪个取决于排序的 tie-break** —— `std::sort`（不稳定）和
> `np.argsort`（稳定）给出的顺序不同。这是同一个物体的两种等优解。
> **② 是 0.00 px**，证明 C++ 实现和标准实现逐位一致。

这验证了：通道索引、`cxcywh→xyxy`、置信度阈值语义、逐类 NMS、argmax 选类
—— 全部和标准实现一致。

**这个验证覆盖不到什么**：反 letterbox 的公式本身没有独立参考
（ultralytics 不做这一步）。它只靠两点保证：
**(a)** 正反变换共用同一份 `LetterboxParams`（数学上互逆）；
**(b)** 框在目视检查中落在目标上。
两者都不如"和另一个实现对比"硬。

### ② 引擎等价性

**关键**：必须把 C++ 前处理的结果 dump 出来喂给 PyTorch，否则比的不是引擎，是预处理。

```
严格 FP32：max|abs| = 1.190e-03, mean = 1.460e-06, 相对 = 1.868e-06
TF32     ：max|abs| = 2.939e+00, mean = 2.150e-03, 相对 = 4.6e-03
```

**TF32 的 raw 误差比严格 FP32 大 3 个数量级，但两者的检出结果完全一致**——
阈值 + NMS 的离散化把误差吃掉了。这说明**"数值误差"和"业务影响"不能混为一谈**。

## 5. 精度 / 性能阶梯

### 5.1 测量方法（这一节比数字重要）

**笔记本 GPU 的主频随温度/功耗在 1.4–2.1 GHz 漂移，同一份代码两次能测出差 2.4 倍的结果。**
所以"跑一次取个值"是不可用的。下面七步是踩出来的：

| # | 问题 | 修法 | 效果 |
|---|---|---|---|
| 1 | 跨进程对比（差 2.4 倍） | **同一进程内对比** | 消除 40% 漂移 |
| 2 | 串行（先测 A 再测 B） | **交错**：每轮把所有引擎各测一遍 | 消除 20% 温漂 |
| 3 | 每引擎一次 `cudaEventSynchronize` | **一轮只同步一次** | 消除 GPU 空闲降频 |
| 4 | 引擎在轮内位置固定 | **轮转起点 `(r+k)%n`** | 消除位置偏差 |
| 5 | 块太短（115 ms ≈ DVFS 反应时间） | **块拉到 460 ms**（200 次/块） | σ 12% → 4.4% |
| 6 | 用"极差"当误差棒 | **σ + 1.96σ/√n** | 23% → ±3.1% |
| 7 | 自检重新加载引擎（分配地址不同） | **`--null-test` 复用同一对象** | 排除混淆 |

**零假设检验（同一个引擎对象测两次）**：

```
比值 = 0.989×    σ = 4.4%    CI = ±3.1%
```

**残余偏差 1.1% < CI 3.1%** → 统计上等于零，方法可用。

**这意味着测量下限约 ±3%**：能分辨 >6% 的差异，分辨不了 1–2%。

### 5.2 四方对比（一次运行内，N 路交错）

```bash
./build/bin/yolov8_demo --engine models/yolov8n_strict.engine \

    --engine2 models/yolov8n_fp16.engine \

```

|---|---|---|---|---|---|
| **FP16** | **2.1038** | **0.754×** | 8318 KB | 8.5% | ±5.9% |
| INT8（QDQ） | 2.4685 | 0.874× | 7981 KB | 4.8% | ±3.4% |
| TF32（默认） | 2.5266 | 0.905× | 13523 KB | 5.1% | ±3.6% |
| FP32 严格 | 2.8531 | 1.000× | 17502 KB | — | — |

### 5.3 结论与显著性

| 对比 | 差异 | 显著性 | 判定 |
|---|---|---|---|
| **FP16 vs FP32 严格** | **快 32.6%（1.33×）** | **5.5σ** | ✅ 可信 |
| **INT8 vs FP16** | **慢 15.9%** | 2.3σ | ✅ 基本可信 |
| TF32 vs FP32 严格 | 快 9.5%（1.11×） | 2.6σ | ⚠️ 边缘 |
| INT8 vs TF32 | 3.5% | **0.7σ** | ❌ **打平** |

> **最后一行的教训**：早期版本报"INT8 比 TF32 快 2.9%"，在新方法下这个差异是噪声。
> **把噪声当结论，是性能测量里最常见的错误。**

### 5.4 精度（mAP@0.5，COCO128 / 128 张）

> **⚠️ 口径提示**：本节是 **128 张 + 自写指标**，用于**三档互相对比**；
> **COCO val2017 全量（5000 张 + pycocotools 官方协议）的结果在 [附录 A](#附录-acoco-val2017-全量-mappycocotools-官方协议)**，
> 那里 **INT8 的掉点是 −1.27 pt（不是 −1.76 pt）** ——
> **小数据集把掉点高估了 0.5 pt**，绝对 mAP 更是高估了 3.3 pt（见 A.4）。
> **对外引用请用附录 A 的数字，本节只用于相对比较。**

| 模型 | mAP@0.5 | 掉点 |
|---|---|---|
| FP32 | 0.5907 | — |
| **INT8**（per-channel, 100 张校准） | 0.5731 | **−1.76 pt** |
| INT8（per-tensor） | 0.5633 | −2.74 pt |
| FP16 | *未实测* → **附录 A 已补：全量 0.5167，与 FP32 在噪声内相同** | **上界 ≈ 0**（见下） |

> **FP16 的 mAP 未实测**：polygraphy 的 `--fp-to-fp16` 和 onnxconverter-common 在
> YOLO 的 `Resize` 节点上都插错了 Cast，产出的 ONNX onnxruntime 加载失败
> （TRT 能容忍，所以 FP16 engine 是好的）。
> **上界论证**：FP16 的数值误差（~1e-3）比 INT8（~1e-2）小一个数量级，
> 检出的坐标偏差也更小（0.8 px vs 1.7 px），所以 FP16 的 mAP 掉点必然 ≤ INT8 的 1.76 pt。

**注意：性能提升远小于 ResNet50**（P2 里 FP32→FP16 是 2.33×，这里只有 1.33×）。原因见 §11。

## 6. INT8：TRT 11 把整条老路删了

**这是本项目最重要的发现。**

```bash
$ grep IInt8Calibrator $TRT_ROOT/include/*.h        → 0 处
$ grep setInt8Calibrator $TRT_ROOT/include/*.h      → 0 处
$ trtexec --help | grep int8                        → 0 处（只剩 DLA 专用选项）
```

**TensorRT 11 删掉了"隐式量化"的整套接口**（`IInt8EntropyCalibrator2`、`BuilderFlag::kINT8`）。
和之前发现的 `BuilderFlag::kFP16` 被删、`destroy()` 被删是同一件事：

> **TRT 11 全面转向 strong typing：精度必须写在 ONNX 里，引擎只负责"照着执行"。**

**所以 INT8 的新路线是 QDQ 显式量化**：

```
ONNX（FP32）
  ↓ onnxruntime.quantization.quantize_static(quant_format=QDQ)
QDQ ONNX（QuantizeLinear / DequantizeLinear，节点里带 scale）
  ↓ TensorRT 直接解析，不需要 calibrator
INT8 engine
```

### 三个必须踩的坑

| # | 报错 | 根因 | 解法 |
|---|---|---|---|
| 1 | `Non-zero zero point is not supported` | **ORT 默认 `ActivationSymmetric=False`**（uint8 非对称） | `extra_options={"ActivationSymmetric": True}` |
| 2 | `input has type Int32 but must be FP8/FP4/Int4/Int8/UInt8` | QDQ 规范里量化 Conv 的 **bias 是 int32**，TRT 不认 | 离线把 int32 bias 折成 float 常量 |
| 3 | 坐标误差 379 px | 把 **Detect 头**（`/model.22/`）也量化了 | 只量化 `Conv`/`MatMul`，排除头部 |

**踩完三个坑后**：INT8 engine 建成功（7981 KB、解析 929 层），检出坐标偏差 **1.7 px**。

## 7. 敏感层定位（分组消融）

没有用 `polygraphy debug precision`（TRT 11 的精度约束接口同样可能已变），
改用**分组消融**：把某一块排除在量化之外，看 mAP 恢复多少。

| 配置 | mAP@0.5 | 掉点 |
|---|---|---|
| FP32 | 0.5907 | — |
| 全量化（backbone + neck） | 0.5731 | −1.76 pt |
| **只量化 neck**（排除 0–9） | **0.5941** | **+0.34 pt（无损）** |
| **只量化 backbone**（排除 10–21） | **0.5654** | **−2.53 pt** |

**结论：敏感区在 backbone（model.0–9），neck（model.10–21）可以安全量化。**

**但这条结论没有实用价值**：backbone 占约 60% 的算力，只量化 neck 等于没省。

## 8. 量化配置对比（W6）

**per-channel vs per-tensor**（同校准集、同数据）：

```
per-channel : 0.5731   −1.76 pt
per-tensor  : 0.5633   −2.74 pt        差 0.98 pt
```

→ **per-channel 明显更好**（每个输出通道独立 scale，避免通道间动态范围被拉平）。

## 9. 七条被证伪的优化 / 假设

### 9.1 GPU NMS 比 CPU 慢 180 倍

| 候选数 | CPU | GPU 总 | GPU 内核 |
|---|---|---|---|
| 46 | **0.0008 ms** | 0.151 ms | 0.018 ms |
| 637 | **0.056 ms** | 0.360 ms | 0.014 ms |

**三层分析**：

1. **表面**：GPU 慢 180 倍
2. **中层**：GPU 里"计算"只占 6–12%，其余是**驱动往返**（2 次 pageable H2D + 1 次 sync + 1 次阻塞 D2H ≈ 120 µs 固定开销）
3. **深层**：**46 个框没有可并行的空间**。即使优化到 pinned + 单次异步，固定开销也要 ~15 µs，仍比 CPU 的 0.8 µs 慢 20 倍

**结论**：生产用 CPU NMS。GPU 版(`--gpu-nms`)保留作实验记录，两版结果**逐位一致**已验证。

**真正的 GPU 方案**是 TensorRT EfficientNMS 的 bitmask + 多轮迭代（只回传结果、不传 n² 矩阵），
那是写 plugin 的工作（P5）。

---

### ⚠️ 9.1.1 本结论被 §19 修正（重要）

上面测的是"**NMS 需要跨主机/设备边界**"的情况。一旦把 decode+NMS 放进**同一个 kernel**
（不跨边界），结论完全反转：

| 场景 | CPU | GPU | 谁快 |
|---|---|---|---|
| 有主机往返（本节上面的数据） | 0.0007 ms | 0.1513 ms | **CPU 快 216×** |
| **同一 kernel 内（§19 的融合 kernel）** | **0.2952 ms** | **0.0296 ms** | **GPU 快 10×** |

**同一个 GPU NMS 算法，唯一变量是"要不要跨边界"。**

所以完整结论是：

> **不是"GPU 不适合 NMS"，是"46 个候选不值得跨一次主机/设备边界"。**
> **一旦 NMS 和 decode 融进同一个 kernel，GPU 快 10 倍。**

**这个修正比原来的结论更有用**——它指出瓶颈在边界，不在算法。

### 9.2 多流并发：收益幅度尚未测准（跨运行数据不可信）

同一实验跑了三次：

| 次 | 串行 | 4 路并发 | 提升 |
|---|---|---|---|
| 1（TF32） | 389 img/s | 486 img/s | 1.25× |
| 2（FP16） | 407 img/s | 600 img/s | **1.48×** |
| 3（FP16） | 434 img/s | 478 img/s | **1.10×** |

**波动来源**：笔记本 GPU 的时钟随温度/功耗漂移，即使同一次运行内串行段和并发段也会碰上不同的频率。

**⚠️ 诚实修正**：上面三个数是**三次独立运行**测出来的，按 §5.1 的标准**都不可信**。

**用配对方法（交错 + 轮转 + 长块）重测后的结果**：

| 版本 | 块长 | 比值 | σ | 95%CI | 能下结论吗 |
|---|---|---|---|---|---|
| 旧（串行测量） | 25 ms | 1.25 / 1.48 / 1.10× | — | — | ❌ 跨运行 |
| 新（交错，块 25 ms） | 25 ms | 0.999 | 20.4% | ±14.1% | ❌ |
| **新（交错，块 270 ms）** | **270 ms** | **0.961** | **16.6%** | **±13.3%** | ❌ |

**块从 25 ms 拉到 270 ms 后 σ 几乎没降** → **瓶颈不是 DVFS，是主机侧调度抖动**：

```
串行 128 张：128 × (enqueue + sync)                    = 256 次驱动调用
多流 128 张：128 × (setTensorAddress×2 + enqueue) + sync = 385 次
```

**WSL2 的 VM 调度抖动直接污染这些调用，而且它是"差模"（两条路径次数不同），
配对测量消不掉。**

**最终结论**：多流收益 4%，但 **CI ±13% > 4%** → **无法证明有收益**。

**理论支持这个结论**：8.7 GFLOPs ÷ 2.1 ms = 4.1 TFLOPS，只占峰值 26%；
YOLOv8n 同时受带宽和 launch 限制，**多流共享同一条带宽** → 不可能有 2× 收益。

**要在车端真正回答"6 路并发能到多少"，得在原生 Linux + Orin 上测**（WSL 的主机抖动不可控）。

### 9.3 校准集分布不是 INT8 掉点的主因

**假设**：校准集用 bus.jpg 增强（街道场景），评测用 COCO128（80 类），
分布不匹配导致 activation scale 估偏。

**实验**：用 COCO128 的图做校准集（同分布、真实多样）。

**结果**：−1.76 pt → **−1.99 pt**（反而略差 0.23 pt，在噪声内）。

**假设被否掉**。正确的结论是：**1.8–2.0 pt 是这套量化方案（只量化 Conv/MatMul、头部留 FP32）的固有水平，与校准集分布基本无关。**

### 9.4 decode 的"缓存局部性优化"只快 9%

**假设**：CPU decode 慢是因为"80 条并发内存流"（channel 在内层，步长 33.6 KB）。
**改成 channel 在外层（单条顺序流）后：0.367 ms → 0.335 ms，只快 9%。**

**真相**：`2.82 MB ÷ 0.335 ms = 8.4 GB/s` = **单核内存带宽上限**。瓶颈是带宽，不是缓存。
真正的解法是把 decode 搬上 GPU（§15）——那里带宽是 384 GB/s。

### 9.5 校准集大小不影响掉点（因为多样性才是关键）

n=10 → 掉 0.44 pt；n=30 → 掉 3.17 pt；n=100 → 掉 1.76 pt。**不单调。**

**原因**：我们的校准集是从**一张图**增强出来的，n 变大不增加多样性，scale 在 n=10 时就饱和了，
后面的差异是 mAP 测量噪声（128 张图，±0.5–1.5 pt）。

### 9.6 引擎内置 NMS（plugin）不划算 —— 它会摧毁 CUDA Graph

详见 §19。一句话：

> **plugin 让"NMS 塞进引擎"变成可能，但 plugin 内部的临时显存分配让引擎无法被 CUDA Graph 捕获。
> Graph 值 1.4 ms，而 NMS 塞进引擎只值 0.06 ms。**

| 方案 | 端到端 |
|---|---|
| 引擎外 GPU decode + Graph | **0.752 ms** |
| 引擎内置 NMS（无 Graph） | 2.467 ms |

### 9.7 我在讲解里犯过的错（也算"被证伪的假设"）

| 错误说法 | 正确 |
|---|---|
| "端到端实测 3.8×" | 2.9 ms 和 0.78 ms 来自**两次不同运行**；应说"由两组配对测量组合推算，约 3.7×" |
| "CI 从 ±13.3% 压到 ±3.1%" | 那是**两个不同实验**的 CI，不能这么比 |
| "差 4% < 3.1%×2 所以测不出" | 判据是 `\|1−ratio\| > CI`，不是 ×2；而且多流的 CI 是 ±13.3% 不是 ±3.1% |
| "Orin 算力约 5060 的 1/5" | **没依据**。按规格粗算是 2–2.5 倍慢（`docs/P5-orin-plan.md` §4） |
| "2.1 ms >> CI" | **单位错**（毫秒 vs 百分比），应换算成 ±0.024 ms 再比 |

## 10. 显存账本（W8）

`--streams 4` 末尾会打印：

```
[W8] 显存账本
  d_img（原图）                2.50 MB   源图缓冲 810x1080
  d_lb（放大图）               1.17 MB   letterbox 640x640
  d_chw（模型输入）            4.69 MB
  d_out（模型输出）            2.69 MB
  我们自己占的合计            11.05 MB
  TensorRT engine              8.12 MB
  本进程总计（估）            19.18 MB
  空闲 / 总显存       6872 / 8150 MB
  多流额外占用                29.52 MB   4 路 × (输入+输出)
```

**但账本里最大的一项不在这张表上**——用 `trtexec` 才能看到：

```bash
$ trtexec --loadEngine=models/yolov8n_fp16.engine --shapes=images:1x3x640x640 --verbose
...
Allocated device scratch memory: 14811648 B = 14.13 MiB
Created execution context with device memory size: 14.1255 MiB
```

> **每个 execution context 需要 14.13 MB 的 scratch（激活值 + workspace），比 engine 文件本身还大。**

**正确的车端显存规划**：

```
每路 = 14.13 MB（context scratch） + 7.38 MB（输入+输出 buffer） = 21.5 MB
6 路 = 129 MB          ← 不是 "engine 8 MB × 6 = 48 MB"
```

**这也是 `MultiStreamRunner` 共享 engine 的意义**：权重只有一份（8.12 MB），
不会因为 6 路并发变成 6 份；但 context 的 scratch 是每路一份，躲不掉。

**想压 workspace**：

```cpp
config->setMemoryPoolLimit(nvinfer1::MemoryPoolType::kWORKSPACE, N);
```
代价：TRT 只能选需要 ≤ N 的 tactic，可能变慢。

## 11. 为什么 FP16 只快 1.33×（而 ResNet50 是 2.33×）

| 模型 | FP32 严格 → FP16 |
|---|---|
| ResNet50（P2） | **2.33×** |
| YOLOv8n（P3） | **1.33×** |

**三个原因**：

1. **参数量小 8 倍**（3.15M vs 25.6M）——FP16 的主要收益之一是权重加载减半，而 YOLO 权重本来就小
2. **层数多、单层小**——融合后仍有上百个 kernel，每个约 2 µs 的 launch 开销与精度无关
3. **不是算力受限**——利用率只有 26%，降精度减的是"算"，而瓶颈在"调度"和"搬运"

> **"降精度能快多少"取决于瓶颈在哪。不测就不知道，猜一定是错的。**

**⚠️ 本节结论已被 §16 修正**：上面那个 1.33× 是**在 CPU 派发没有被消除的情况下**测的。
用 CUDA Graph 去掉 1.4 ms 的 CPU 开销后，FP16 相对 TF32 的真实收益是 **2.13×**
（graph: 1.3451 vs 0.6318 ms）。

**所以"FP16 只快 1.33×"的主因不是"模型太小"，而是"分母里混了和精度无关的 CPU 时间"。**
上面列的三条原因（参数量小 / 层多单层小 / 不是算力受限）里，
**第 2、3 条其实是"CPU 派发占比高"的另一种说法**。

## 13. 已知限制

1. **FP16 的 mAP 未实测**（§5 的上界论证代替）。
2. **校准集只有 100 张、来自一张图**，多样性不足；生产必须覆盖实际场景。
3. **mAP 在 COCO128 上测**（128 张、71 个类），噪声约 ±0.5–1.5 pt；
   差距小于 1 pt 的结论不可靠。而且 coco128 是模型的训练集子集，**绝对值偏高**，
   但**相对掉点**仍然有效（三个模型同一批图、同一个脚本）。
4. **INT8 只量化了 Conv/MatMul**，其余算子保持 FP32，因此 engine 只小 41% 而非 75%。
5. **`MultiStreamRunner` 是单线程提交**（一个 context 不能被多线程同时 enqueue）；
   真正的"多线程 + 每线程一个 context"没做。
6. **前处理和 ultralytics 有差异**：我们用 PIL 风格的双线性 + letterbox，
   ultralytics 用 cv2；边缘目标会有几个像素的差异。
7. **没做 Nsight 分析**（WSL 下 `nsys` 因 WDDM 调试接口不可用）。
8. **测量不确定度约 ±3%**（§5.1 的零假设检验）：能分辨 >6% 的差异，
   **分辨不了 1–2%**。所有"快点/慢点"的结论都必须带上这个误差棒——
   §5.3 里 `INT8 vs TF32` 只有 0.7σ，**只能说打平**。
9. **多流并发（§9.2）的数字是跨运行测的，不可信**，需要按 §5.1 的方法重测（P4）。
11. **服务（§17）是模拟**：反复用同一张图，没有相机采集、传输、ISP。
    它测的是"计算延迟"，不是"相机到输出的端到端延迟"。
12. **没有 Orin 数据**。`docs/P5-orin-plan.md` 给了完整方案，但**执行需要硬件**。
    简历上只能写"在 RTX 5060 上验证"，不能写"部署到车端"。
13. **点云部分只做了 pillarization**（§18），没有训练好的 BEV 模型和数据集，
    无法做端到端 BEV 检测。
14. **没有 p99 的车端验证**：§17 的分位数是在笔记本上测的，
    Orin 上的 p99 必须重测（降频、功耗墙都不同）。
10. **端到端延迟已补齐（实测，FP16 / bus.jpg）**：

    | 阶段 | 耗时 | 占比 |
    |---|---|---|
    | preprocess | 0.043 ms | 1.5% |
    | infer | 2.023 ms | 71.8% |
    | **D2H（2.69 MB）** | **0.417 ms** | **14.8%** |
    | **decode + 反 letterbox** | **0.335 ms** | **11.9%** |
    | NMS | 0.001 ms | 0.0% |
    | **合计** | **2.819 ms** | 100% |

    **早期版本报的"合计"只含 preprocess+infer = 2.066 ms，低估了 0.753 ms（27%）。**

    **这两项本质是同一个瓶颈**：
    ```
    D2H    2.69 MB ÷ 0.417 ms = 6.4 GB/s   （PCIe 速率）
    decode 2.82 MB ÷ 0.335 ms = 8.4 GB/s   （单核内存带宽）
    ```
    **都是"摸 2.7 MB"的代价。** 试过把 decode 的遍历改成通道优先（单条顺序流，
    消除 80 条并发内存流），只快了 9% —— **说明瓶颈是带宽，不是缓存局部性**。

    真正的解法是**把 decode 搬到 GPU**：2.8 MB 在 GPU 上只需 ~7 µs（384 GB/s），
    只回传 46 个框（1.1 KB），D2H 从 0.417 → ~0.005 ms。
    **预期省 0.73 ms（26%）——比整个 FP16 加速（0.70 ms）还多，且零精度损失。**
    **这个问题已解决，见 §15**（GPU decode，省 0.634 ms，零精度损失）。

## 15. P4 第一项：decode 搬上 GPU（−0.63 ms，零精度损失）

### 15.1 问题：27% 的时间不在推理里

补齐延迟拆解后发现（FP16 / bus.jpg）：

```
preprocess 0.043  +  infer 2.023  +  D2H 0.433  +  decode 0.341  +  NMS 0.001
                                  └──────┬──────┘
                                    占 27%
```

**这两项本质是同一件事：把 2.7 MB 摸两遍。**

```
D2H    : 2.69 MB ÷ 0.433 ms = 6.2 GB/s   （PCIe）
decode : 2.82 MB ÷ 0.341 ms = 8.3 GB/s   （单核内存带宽上限）
```

**试过的无效优化**：把 decode 的遍历从"anchor 外层 / class 内层"改成
"class 外层 / anchor 内层"（消除 80 条并发内存流）——**只快 9%**。
这证明瓶颈是带宽，不是缓存局部性。

### 15.2 做法：kernel 挑完再回传

```
改前：GPU 推理 → D2H 2.69 MB → CPU 扫 2.82 MB
改后：GPU 推理 → GPU kernel（挑出 46 个框）→ D2H 1.1 KB
```

kernel 是一个线程一个 anchor：argmax over classes → 阈值过滤 → `atomicAdd` 追加到紧凑数组。
主机侧复用显存（绝不每帧 `cudaMalloc`），只回传 `count(4 B)` + `dets(46×6×4 = 1.1 KB)`。

**一个反直觉的关键点**：

> **CPU 上"跨 33.6 KB 步长访问"是灾难（80 条并发内存流，超出预取器能力），
> 但 GPU 上同一个模式是完美合并的**——因为线程是内层维度，
> 相邻线程读相邻地址，一个 warp 的一次 load 正好覆盖 128 字节。

所以 GPU kernel 保持"通道在外、anchor 在内"的线程映射，不做 CPU 那套重排。

### 15.3 结果（同一次运行内对照，不跨运行减）

| 路径 | D2H | decode | 合计 |
|---|---|---|---|
| **CPU decode** | 0.433 ms | 0.341 ms | **0.774 ms** |
| **GPU decode** | ~0.000 ms | **0.140 ms** | **0.140 ms** |
| | | 其中纯 kernel | **0.027 ms** |

**省 0.634 ms（82%）。**

**正确性校验（代码内置，每次运行都打）**：

```
✅ 与 CPU 版一致（46 vs 46 个，坐标差 0.0000 px，分数差 0.000000）
```

零精度损失——因为 GPU 和 CPU 算的是同一个 argmax，只是搬运量从 2.69 MB 变成 1.1 KB。

### 15.4 剩下那 0.113 ms 是什么

```
纯 kernel 0.027 ms  →  含回传 0.140 ms      差 0.113 ms
```

**1.1 KB 的数据要 0.113 ms**，因为：

```cpp
cudaMemcpy(&num_hit, count, 4 字节, D2H);          // 阻塞：一次驱动往返 + 一次设备同步
cudaMemcpy(h.data(), dets, 1104 字节, D2H);        // 再来一次
```

**和 GPU NMS 那个 120 µs 固定开销是同一件事**：
**主机/设备边界的往返代价与传输量几乎无关。**

**还能再省**：把 `count` 和 `dets` 放进同一个 buffer，一次拷贝；再配 pinned 内存。
预计 0.113 → ~0.02 ms。**留作下一步。**

## 16. CUDA Graph：真正的瓶颈是 CPU 派发（−1.38 ms，零精度损失）

### 16.1 结果（先用 NaN 验证，再信性能）

```
输出校验（两边都先把 d_out 填成 NaN 再跑）
  直连 vs Graph 的 max|abs| = 0.000e+00     ← 逐位相同
  Graph 输出里残留的 NaN   = 0 / 705600
  ✅ 输出一致 → Graph 确实做了同样的计算

直连 enqueue : 2.0143 ms
Graph 重放   : 0.6294 ms
比值         : 0.313 ± 4.2%（95%CI）   →  省 1.3849 ms（68.8%）
```

**为什么必须先填 NaN**：如果捕获的图是空的，`d_out` 会保留上一次的值，
直接比较会"相等"，而时间会显示"更快"。填 NaN 之后，图若没干活，输出里就留有 NaN。

### 16.2 为什么比预估大 7 倍

我原本按"100 个 kernel × 2 µs launch ≈ 0.1–0.2 ms"估的，实测 1.38 ms（13.8 µs/kernel）。
真相是：

```
我们一直报的 "推理 2.0 ms"
  = GPU 真正算的 0.63 ms
  + CPU 侧派发 1.38 ms          ← 68%
```

**重新算利用率**：

```
8.7 GFLOPs ÷ 0.63 ms = 13.8 TFLOPS
TF32 峰值 ≈ 15 TFLOPS  →  92%
```

**不是 26%，是 92%。** 所以 YOLOv8n 在这张卡上是**算力接近饱和**的，
之前"带宽受限 / 利用率只有 26%"的判断，分母里混进了 CPU 时间。

### 16.3 这一个原因解释了四条早先的困惑

| 早先的观察 | 真正的原因 |
|---|---|
| "GPU 利用率只有 26%" | 分母 2.0 ms 里 68% 是 CPU 开销 |
| "多流并发测不出收益（CI ±13%）" | **CPU 是瓶颈，加流不减少 CPU 工作** |
| "FP16 只快 1.33×（ResNet50 是 2.33×）" | FP16 只减 GPU 的 0.63 ms，CPU 的 1.38 ms 不变 |
| "INT8 反而不划算" | 同理：量化减算力，不减派发 |

**四条互相矛盾的结论，一个原因全解释通了。**

### 16.4 两个零精度损失的优化叠加

| 优化 | 前 | 后 | 省 |
|---|---|---|---|
| **GPU decode**（§15） | D2H 0.417 + decode 0.338 = 0.755 ms | 0.086 ms | **−0.669（89%）** |
| **CUDA Graph** | 推理 2.042 ms | 0.629 ms | **−1.413（69%）** |
| **端到端（实测）** | **2.9 ms** | **0.75–0.78 ms** | **约 3.8×** |

**`--gpu-decode --cuda-graph` 的实测拆解**：

```
preprocess : 0.036 ms
infer      : 0.629 ms   （Graph 重放）
decode     : 0.086 ms   （GPU，纯 kernel 0.026）
D2H        : 0.000 ms   （只回传 1.1 KB）
NMS        : 0.001 ms
────────────────────────────
合计       : 0.75 - 0.78 ms   ← 真实端到端（跨运行波动 ±4%，测量噪声）
```

**两项都是零精度损失**（decode 坐标差 0.0000 px；Graph max|abs| = 0）。

> **注意精度**：端到端实测在 **0.751 ~ 0.781 ms** 之间波动（±4%），
> 与 §5.1 定下的 ±3.1% 测量不确定度一致。
> **所以写"0.76 ms"或"约 3.8×"是诚实的，写"0.751 ms"是假精度。**
**而 INT8 折腾了半天是 −1.76 pt 且更慢。**

### 16.5 约束（这三条写错就崩）

```cpp
// ① 必须在非默认流上捕获 —— TrtEngine::stream() 是 cudaStreamCreate 建的
cudaStreamBeginCapture(engine.stream(), cudaStreamCaptureModeThreadLocal);

// ② 捕获期间不能有任何同步 —— 所以用 enqueueDevice() 而不是 inferDevice()
graph.capture(engine.stream(), [&] { engine.enqueueDevice(d_chw, d_out); });

// ③ 图绑定 d_chw / d_out 的地址与形状 —— 换 batch / 换图尺寸必须重新捕获
cudaGraphInstantiate(&exec_, graph_, 0);
```

为了满足 ②，`TrtEngine` 新增了 `enqueueDevice()`（只提交、不同步）
和 `stream()`（暴露内部流）。

**下一步**：既然 GPU 时间现在成了瓶颈（0.63 ms），
**Graph + FP16 vs Graph + TF32** 应该能测出 FP16 的真实收益——
之前那个 1.33× 是被 CPU 开销稀释过的。

---
### 16.6 附赠发现：FP16 的真实收益是 2.13×（不是 1.33×）

同一个 Graph 路径下换引擎：

| 引擎 | 直连 enqueue | **Graph 重放** | CPU 派发（差值） |
|---|---|---|---|
| TF32 | 2.3807 ms | **1.3451 ms** | 1.04 ms |
| **FP16** | 2.0416 ms | **0.6318 ms** | 1.41 ms |

```
1.3451 ÷ 0.6318 = 2.13×
```

**§5 里测到的 1.33× 是 2.9 → 2.2 ms —— 分母里混了 1.4 ms 的 CPU 开销。**
去掉 CPU 开销后，FP16 在 GPU 时间上的真实收益是 **2.13×**。

**所以"FP16 为什么只快 1.33×"这个问题的答案不是"模型太小"，
而是"测量里混进了和精度无关的 CPU 开销"**（§11 的解释需要按此修正）。

## 17. 服务化：从"跑一次"到"帧循环 + 分位数"

前面所有数字都是**中位数**。车端的判据是 **p99 / 最大值**——平均 0.77 ms 只说明平时够用，
p99 才是"会不会撞车时晚一米"。

`src/service.cpp` 就是答案：一个帧循环，每帧记延迟，最后出分位数和直方图。

```bash
./build/bin/yolov8_service --engine models/yolov8n_fp16.engine \
    --image models/bus.ppm --frames 2000 --cameras 6 --csv dump/lat_opt.csv

# 对照：不做优化的路径
./build/bin/yolov8_service --engine models/yolov8n_fp16.engine \
    --image models/bus.ppm --frames 2000 --cameras 6 --cpu-path --no-graph
```

### 17.1 结果（各 2000 帧）

| 指标 | 基线（CPU decode + 直连） | 优化后（GPU decode + Graph） | 改善 |
|---|---|---|---|
| min | 2.062 ms | 0.722 ms | 2.86× |
| **p50** | **2.326 ms** | **0.771 ms** | **3.02×** |
| p90 | 2.661 ms | 0.802 ms | 3.32× |
| **p99** | **3.350 ms** | **0.834 ms** | **4.02×** |
| p99.9 | 5.185 ms | 0.877 ms | **5.91×** |
| max | 5.944 ms | 1.220 ms | 4.87× |
| **超预算帧** | **1 / 2000** | **0 / 2000** | — |

### 17.2 最重要的发现：尾部改善远大于中位数

```
p50   改善  3.02×
p99   改善  4.02×
p99.9 改善  5.91×      ← 越往尾部越猛
```

看抖动比：

| | 基线 | 优化后 |
|---|---|---|
| p99 / p50 | **1.44** | **1.08** |
| p99.9 / p50 | 2.23 | 1.14 |
| max / p50 | 2.55 | 1.58 |

**基线路径的每一帧都要做**：`cudaMemcpy` 2.69 MB（pageable，驱动内部 staging）、
CPU 扫 2.82 MB、`std::vector` 分配、100+ 次 kernel launch。

**这些动作的耗时取决于"当时系统在干什么" → 尾部被拉长。**
Graph + GPU decode 把这些全砍了，CPU 几乎不参与 → 抖动源消失。

### 17.3 车端翻译

```
6 路 × 30 fps = 180 帧/秒
基线：2000 帧 ÷ 180 ≈ 11 秒 → 1 次超预算
     → 每 11 秒掉一帧，30fps 下肉眼可见
优化后：2000 帧零超预算，max 只占预算 22%
```

> **只看 p50 会说"快了 3 倍"；真正的价值是"从每 11 秒掉一帧变成零超时"。**

### 17.4 诚实边界

| 真实的 | 这里的 |
|---|---|
| 从相机取帧（V4L2/GMSL/RTSP） | 反复用同一张 `bus.ppm` |
| 帧到达时间戳、可能丢帧 | 固定循环 2000 次 |
| 多线程、多路并发 | 单线程轮询（`--cameras` 只影响预算计算） |

**它测的是"计算延迟"，不是"相机到输出的端到端延迟"**——后者还要加采集、传输、ISP，
必须上真硬件才能测（见 `docs/P5-orin-plan.md`）。

## 18. 点云 pillarization：BEV 的第一道坎（含验证强度分级）

PointPillars / CenterPoint 的第一步：把无序点云散进规则的柱状网格。

**TensorRT 做不了这件事**，原因有两个，都是硬性的：

| 需求 | TRT 支持吗 |
|---|---|
| 两个点落进同一格 → 合并进同一根 pillar | ❌ 要原子分配编号 |
| 有几根 pillar **只有算完才知道** | ❌ 输出形状是动态的 |
| ONNX 有对应算子吗 | ❌ `ScatterND` 语义不同（索引要预先给定） |

所以只能写 kernel，再包成 plugin。

### 18.1 算法（每线程一个点）

```cuda
int ix = floor((x - min_x) * inv_voxel_x);      // 落在哪个格子
int iy = floor((y - min_y) * inv_voxel_y);
int cell = iy * grid_x + ix;

int pid = atomicCAS(&cell_to_pid[cell], kNoPillar, kClaiming);   // 抢 pillar 编号
if (pid == kNoPillar) { pid = atomicAdd(num_pillars, 1); ... }
else if (pid == kClaiming) { /* 自旋等 */ }

int slot = atomicAdd(&counts[pid], 1);          // 在该 pillar 里抢槽位
pillars[pid][slot][c] = pt[c];
```

### 18.2 两个真实的并发 bug（都是自检抓出来的）

**bug 1：自旋等待没有 `volatile` → 死循环**

```cuda
// ❌ 编译器看到循环体没写 cell_to_pid[cell]，可以把"读"提到循环外
while ((pid = cell_to_pid[cell]) == kClaiming) { ... }   // -2 永远不变 → 卡死

// ✅ 必须强制每次都从内存重读
volatile int* slot = &cell_to_pid[cell];
while ((pid = *slot) == kClaiming) __nanosleep(64);
```

**表现为"程序卡住"**——你能发现。

**bug 2：发布 pillar 编号前没完成初始化 → 数据静默出错**

```cuda
// ❌ 先公开 pid，别的线程立刻 atomicAdd(&counts[pid], 1)
atomicExch(&cell_to_pid[cell], pid);
counts[pid] = 0;          // ← 把这行的 1 覆盖回 0 → 那个点的计数丢了

// ✅ 先造好，再屏障，最后发布
counts[pid] = 0;
coords[...] = ...;
__threadfence();                        // 保证上面的写对别人可见
atomicExch(&cell_to_pid[cell], pid);    // 最后才公开
```

**表现为"不卡、不报错、只是 69 个格子的数据错了"**——只有自检才抓得到。

> **修前：`pillar 数一致，但 69 个格子点内容不同、丢失 71 个点`**
> **修后：`50000 点 → 28403 根 pillar，存下 50000 点（100.0%），✅ 完全一致`**

### 18.3 验证方法：五层，每层防不同的错

**不能按顺序比**——原子操作让 pillar 内点的顺序不确定。

| 层 | 做什么 | 防什么错 |
|---|---|---|
| **0. 对比器自检** | 用 4 个手写小数组检验"对比函数本身" | **测试工具"往通过方向错"** |
| 1. 手算 3 点 | 3 个点、故意让 2 个落在同一格 | 格子映射公式错 |
| 2. 定义级不变量 | 见 §18.5，**不需要参考实现** | 点被丢、格子重复、数量不守恒 |
| 3. NumPy 原语参考 | `np.unique` + `np.lexsort`，全向量化 | 公式化写错 |
| 4. 我的 CPU 循环 | 同源代码顺跑一遍 | 实现不一致（**自证**） |

#### 第 0 层为什么必须有（真实教训）

第一版的对比函数用 `np.sort(a, axis=0)`——**那是逐列排序**，会把行拆散：

```python
A = [[1,2], [3,4]]
D = [[1,4], [3,2]]          # 完全不同的两个点集
np.sort(A, axis=0) → [[1,2],[3,4]]
np.sort(D, axis=0) → [[1,2],[3,4]]     # ← 也被排成了这个！
→ A 和 D 被判成"相同"
```

**后果不是测试失败，而是测试失去意义**——第 ③ 层永远通过。

修法：改用 `np.lexsort`（按列字典序排整行），**并把反例钉进代码**：

```python
assert not np.array_equal(sorted_rows(A), sorted_rows(D)), "对比器有 bug"
# 同时确认逐列排序确实会误判，防止以后有人"优化"回去
assert np.array_equal(np.sort(A, axis=0), np.sort(D, axis=0))
```

> **验证工具本身也需要被验证。**
> **最危险的测试 bug 不是误报失败，而是误报通过。**

#### 集合对比怎么做（第 3、4 层共用）

1. 把两边都转成 `map<格子坐标, 该格子的点列表>`（键用 `(iy, ix)`）
2. **把每根 pillar 的点按整行排序**（抵消原子操作带来的顺序不确定）
3. 逐格比较：点数相同 + 排序后逐元素相等

#### 测试参数必须避开"合法的非确定性"

```cpp
p.max_pillars = 60000;          // 实际只用 28403 → 不会溢出
p.max_pts_per_pillar = 32;      // 实测最密 8 点 → 不会截断
```

**如果这两个上限被突破，GPU 和 CPU 的结果会"合法地不同"**（哪些点被丢弃取决于线程到达顺序），
测试会误报失败。**必须排除这种情况，否则真 bug 会被假报警淹没。**

### 18.4 性能

```
50000 点 → 28403 根 pillar：0.0368 ms（含每次 memset 清表 160 KB）
```

**注意那个 memset**：`cell_to_pid` 有 4 万个 int，每次要填 -1。这是一个真实开销，
优化方向是用 epoch 标记代替清零。

### 18.5 验证强度分级（必须诚实）

> **一个必须承认的问题**：`pillarizeCpu()` 是我自己写的，和 kernel 共享同一套理解。
> **它只能抓"两个实现不一致"，抓不到"我对 pillarization 的语义理解错了"。**

所以给每一层验证标注它到底能证明什么：

| 层 | 对照物 | 独立性 | 能证明 | 不能证明 |
|---|---|---|---|---|
| **0. 对比器自检** | 4 个手写反例数组 | ✅ 反例驱动 | **测试工具不会"往通过方向错"** | 被测对象是否正确 |
| **1. 手算 3 点** | 人脑按公式算 | ✅ 独立 | 格子映射公式没错 | 50000 点竞争下会怎样 |
| **2. 定义级不变量** | 无（检查定义本身） | ✅✅ **不需要参考实现** | **没有点被静默丢弃、没有格子重复、数量守恒** | 语义理解是否符合主流实现 |
| **3. NumPy 原语参考** | `np.unique` + `np.lexsort` | ⚠️ 中等（库可信，胶水是本人写的） | 公式化写错（循环 vs 向量化两条路） | 同上 |
| **4. 本人 CPU 循环** | 同源代码 | ❌ **自证** | 实现一致性 | 几乎不能证明"对" |

**第 2 层是最有价值的**，因为它问的问题不需要任何参考答案：

> **"我输入的 5 万个点，是不是每一个都能在输出里找到？"**
> **只要有一个找不到，就一定错了——不需要知道正确答案是什么。**

检查项（`checkInvariants()`）：
1. 没有两根 pillar 共用同一个 `(iy, ix)`
2. 每根 pillar 的 `(iy, ix)` 都在 `[0, grid)` 内
3. **每个界内输入点必须能在输出里找到**（按 4 个特征的浮点位模式做多重集合比对）
4. 界外点数 + 存下点数 == 输入点数
5. 每根 pillar 存下的点数 ≤ `max_pts_per_pillar`

第 3 条的实现是**用 multiset 逐点核对**——§18.2 那个"丢 71 个点"的 bug，
这一层能独立抓出来，不依赖 CPU 参考。

### 18.6 还没做的：和生产实现对齐

## 19. 引擎内置 NMS（E2E）与 CUDA Graph 互斥

ultralytics 可以导出带 NMS 的 ONNX（`export(..., nms=True)`），输出直接是 `[1,300,6]` 最终框。
我们实测了这条路，结论是**不划算，而且原因是结构性的**。

### 19.1 三方对拍：我们的 kernel 和官方 plugin 等价

| 来源 | person | bus |
|---|---|---|
| ultralytics PyTorch | 4 个 + 1 辆 | — |
| **我们的 decodeV8 + nms** | `[670.4, 380.5, 809.0, 879.6]` | `[34.4, 229.5, 797.3, 767.0]` |
| **TRT 内置 EfficientNMS** | `[670.4, 380.6, 809.0, 879.7]` | `[34.4, 229.5, 797.3, 766.9]` |
| 差 | **0.1 px** | **0.1 px** |

**我们手写的 kernel 和 TensorRT 官方 plugin 输出等价（0.1 px）。**

顺带一个有意思的差异：**ONNXRuntime 跑同一个模型，bus 框是 `[30.9, 231.2, 800.7, 777.6]`，
和 TRT 差 10 px（IoU 0.972）**——两者在 NMS 的 `TopK` 上对"分数相同的近重复候选"排序不同。
TRT 的选择恰好和我们的贪心顺序一致。

### 19.2 `[1,300,6]` 的六列语义（必须实测确认）

```
 477.6471  227.8950  560.0080  521.4577  0.8962  0.0000
 ...
  98.2964  137.0076  554.4891  460.8587  0.8362  5.0000    ← cls=5 是 bus
```

**结论：`[x1, y1, x2, y2, score, cls]`，坐标在 640 letterbox 空间，`box_coding = BoxCorner`。**
（ultralytics 在 ONNX 图里已经做了 cxcywh→xyxy，`score_activation` 也不再做 sigmoid。）

**这是本项目第 4 次"同一批数字不同布局"的坑**——前三次是通道在前、cls 在末列、COCO 的 xywh。
**四次都不报错，只输出错的结论。**

### 19.3 致命问题：E2E 引擎不能被 CUDA Graph 捕获

```
[TRT] enqueueV3: cudaError 900: operation not permitted when stream is capturing
[TRT] [defaultAllocator::deallocate] Error Code 1: invalidargument
```

**`cudaErrorStreamCaptureUnsupported`**：EfficientNMS 在每次 `enqueue` 时**分配/释放临时显存**
（日志里的 `deallocate` 就是证据），而 CUDA Graph 捕获期间**禁止任何显存分配/释放**。

**这不是 bug，是设计冲突**：

> **想要"引擎内部完成 NMS" → 用 plugin → plugin 内部要临时显存 → 不能 Graph**
> **想要"Graph 捕获" → 引擎必须无状态、无临时分配 → 后处理只能放在引擎外**

### 19.4 三方案对决

| 方案 | 输出 | 回传 | 能否 Graph | 端到端 |
|---|---|---|---|---|
| **A** 原始布局，CPU decode + NMS | `[1,84,8400]` | 2.69 MB | ✅ | 2.8–3.5 ms |
| **B** 引擎外 GPU decode kernel | 46 框 | **1.1 KB** | ✅ | **0.752 ms** |
| **C** 引擎内置 NMS（EfficientNMS） | 300 框 | 7.03 KB | ❌ | **2.467 ms** |

**B 赢 C 3.3 倍。原因不是回传量，是"能不能 Graph"。**

Graph 值 1.4 ms，而"NMS 塞进引擎"只值约 0.06 ms。

### 19.5 所以"自己写 plugin"这个方向被数据否掉了

原计划要写一个 IPluginV3 把我们的 decode+NMS kernel 包进引擎。**现在有数据说不用写**：

| 收益 | 代价 |
|---|---|
| 省掉 decode kernel（0.026 ms） | **失去 CUDA Graph（−1.4 ms）** |
| 回传更"干净"（下游零代码） | 引擎多了 300 行零填充（7.03 KB vs 1.1 KB） |

> **在这个项目里，写 plugin 的收益（约 0.06 ms）远小于代价（1.4 ms）。**
>
> **但"为什么不该写"这个分析，比"我写了一个 plugin"更有价值。**

**什么时候该写 plugin**：模型里有 TRT 不支持的算子（如 18 节的点云 scatter），
**不写就跑不起来**——那才是 plugin 的正确用途。
### 19.6 补记：一个"把 fp32 写成 fp16 名字"的转换脚本

**在为附录 A 重做 FP16 模型时踩到的，是整份文档里最典型的"静默错误"。**

我重写了 `to_fp16.py`，让它依次试三个 backend：

```
ort  → onnxruntime.transformers.float16（首选）
occ  → onnxconverter-common（旧路径，Resize 上有 bug）
none → 不转换，直接复制（诊断用）
```

**判据只有一条：转完让 ORT 试着加载，能加载就算成功。**

**结果 `ort` 和 `occ` 都失败，`none` "成功"了** —— 于是脚本打印：

```
[OK] 用 backend=none 转换成功
写入 models/yolov8n_fp16.onnx  (12.3 MB)
```

**问题：`none` 是"没转换"，它写出去的是**原封不动的 fp32 模型**，只是文件名叫 `_fp16`。**

**12.3 MB 就是 fp32 的大小；真 fp16 是 6.2 MB。**

### 为什么这个错误比"转换失败"更危险

| 现象 | 看起来的解读 | 真相 |
|---|---|---|
| ORT 加载成功 | 转换成功 | 加载的是 fp32 |
| mAP 和 FP32 一模一样 | **FP16 零掉点，太好了** | 压根没测 FP16 |
| 文件 12.3 MB | 没注意 | fp32 就是 12.3 MB |

**如果我当时没看那个 12.3 MB，就会得到"FP16 零掉点"这个假结论 —— 而且它完全合理、符合预期、不会引起任何怀疑。**

### 两条修法

```python
# ① none 是诊断用的，绝不写目标文件
if b == "none":
    print("  [诊断] 源模型可加载（说明问题在转换器，不在源模型）")
    print("         但这是 fp32，不写入 --out")
    continue

# ② 体积自检：一个跟正确性无关、但一眼能看穿的旁证
if ratio > 0.85:
    print(f"[WARN] 体积比 {ratio:.2f} 太接近 1 —— 这不像真的转成了 fp16")
```

**最终成功时打印的是 `(6.2 MB, 源 12.3 MB, 比 0.50)` —— 这个 0.50 才是"真转换了"的证据。**

### 顺带一个被推翻的解释

我一开始说"ORT 转换器能过，是因为它先做符号形状推导"。**打印出真实签名后发现：这个版本根本没有 `use_symbolic_shape_infer` 参数** —— 那件事没发生。

**真正的原因只是：它是另一套 Cast 插入实现，没那个 bug。**

> **结论对，不等于原因对。这两件事必须分开检查。**

## 20. 一句话总结

> **YOLOv8n 上 INT8 没有价值区间**：全量化 −1.76 pt 且比 FP16 慢 7.7%；
> 只量化 backbone −2.53 pt；只量化 neck 无损但性能无收益。
> 分组消融定位到**敏感区在 backbone（0–9）**，neck（10–21）可安全量化。
>
> **最终选 FP16：精度损失 ~1e-3、速度 1.33×（95%CI ±5.9%）、engine 8.1 MB。**
>
> **而真正的瓶颈不在精度，在搬运**：端到端 2.9 ms 里有 27% 是把 2.69 MB 输出
> 搬回主机（0.433 ms）再加 CPU 解码（0.341 ms）。把 decode 搬上 GPU 后
> **这两项从 0.774 降到 0.140 ms（省 82%）**，且零精度损失。
> **"先量清楚时间花在哪"比"早一点开始优化"重要得多。**
>
> **而最后发现：真正的瓶颈不是精度、不是带宽，是 CPU 派发。**
> `infer 2.0 ms` 里 GPU 只算 0.63 ms，另外 **1.38 ms 是 CPU 在逐个派发 kernel**。
> 用 CUDA Graph 把这一百多个 kernel 变成一次提交，**推理 2.014 → 0.629 ms（−68.8%），
> 输出逐位相同（max|abs| = 0）**。
>
> **两个零精度损失的优化（GPU decode + CUDA Graph）合计省 2.15 ms，
> 端到端实测 2.9 → 0.75–0.78 ms（约 3.8×）—— 而 INT8 是 −1.76 pt 且更慢。**
>
> **附带发现：去掉 CPU 开销后，FP16 的真实收益是 2.13×（不是 1.33×）。**
> **我们之前所有"精度-性能"的结论，分母里都混着和精度无关的 CPU 派发时间。**
>
> ---
>
> **P5 之后又补了三件事，它们的共同点是"先写自检，再谈结论"：**
>
> **① 服务化（§17）**：从"跑一次"变成"2000 帧的帧循环"，拿到了 p50/p99/max。
> 发现**尾部改善（5.9×）远大于中位数改善（3.0×）**——因为抖动源就是 CPU 参与。
> 基线每 11 秒掉一帧，优化后零超时。
>
> **② 点云 scatter（§18）**：BEV 的必踩坑（TRT 不支持原子分配 + 动态输出）。
> 写这个 kernel 抓到了**两个真实的并发 bug**——`volatile` 缺失导致死循环、
> 半成品发布导致 69 个格子数据静默出错。**后者不报错，只有自检能抓。**
>
> **③ 引擎内置 NMS（§19）**：证明我们的 kernel 和 TensorRT 官方 plugin 等价（0.1 px），
> 但也证明**它和 CUDA Graph 互斥**（plugin 内部要临时显存 → 不能捕获）。
> 于是"自己写 plugin"这个方向被数据否掉——**省 0.06 ms，赔 1.4 ms。**
>
> **三轮下来，最有价值的产出还是同一个：先造参考、先写自检、再下结论。**
>
> **而 TRT 11 删掉 calibrator 这件事，比掉点本身更值得记**：
> 它意味着网上所有 TRT 8.x/10.x 的 INT8 教程都不适用了。

## 附录 A：COCO val2017 全量 mAP（pycocotools 官方协议）

> 正文里的 mAP 是在 **coco128（128 张）** 上用自写指标测的，适合做"三档互相对比"；
> 但**不能对外引用**（既不是官方指标，也不是完整验证集）。
> 这一节补上 **5000 张 + pycocotools** 的结果。

### A.1 为什么要重测

| 问题 | 具体 |
|---|---|
| **数据集太小** | 128 张 → 统计强度弱，而且**会系统性夸大差异**（下面有量化） |
| **指标非官方** | 单 IoU(0.5) + 101 点插值，不是 COCO 的 mAP@0.5:0.95 |
| **没有外部锚点** | 自己测的数字，无法判断"流水线到底接对没有" |

### A.2 结果

**环境**：ONNXRuntime CPU（三档同一工具链）、`conf=0.001`、NMS IoU=0.7、letterbox 640

| 档位 | mAP@0.5:0.95 | mAP@0.5 | mAP@0.75 | 检出框数 | 相对 FP32 | **同进程 ms/张** |
|---|---|---|---|---|---|---|
| **FP32** | **0.3668** | **0.5165** | 0.3987 | 857,548 | 基准 | **135** |
| **FP16** | 0.3669 | 0.5167 | 0.3988 | 858,817 | **≈ 0（噪声内）** | **61** |
| **INT8** | 0.3552 | **0.5038** | 0.3870 | 949,474 | **−1.27 pt** | **97** |

**速度列的口径**：**同一个进程里依次跑三个模型**（`--models a b c`），脚本自报的纯推理均值。
**必须是同进程** —— 本项目在项目② 里量过：同一份 engine 跨进程/跨运行能差 16%（最大见过 2.4×）。

**换算**：FP16 比 FP32 快 **2.21×**；INT8 只有 **1.39×**，**比 FP16 还慢 59%**。

> **注意这是 CPU 上的数（ORT CPUExecutionProvider），不能和正文的 GPU/TRT 延迟混着比。**
> CPU 上 fp16 快是因为权重文件小一半（6.2 vs 12.3 MB）、访存少，
> 而 ORT CPU 对 int8 的 kernel 支持不如 fp16 的"加载时转 fp32"路径成熟。

### A.3 外部锚点：和官方数字对得上

**YOLOv8n 在 COCO val2017、640 输入下的官方 mAP@0.5:0.95 = 0.373。**

| | mAP@0.5:0.95 | 与官方差 |
|---|---|---|
| 官方 yolov8n | 0.373 | — |
| **本项目 FP32** | **0.3668** | **−0.62 pt（1.7%）** |

**这是整个项目里唯一"不靠自己验证自己"的证据** —— 说明
**letterbox → ONNX → decode（通道在前）→ NMS → 坐标还原** 这一整条链路都是对的。

### A.4 三个由这组数据得出的结论

#### ① 小数据集会**系统性夸大**差异（两个独立证据）

| 量 | 128 张（coco128） | 5000 张（val2017） | 偏差 |
|---|---|---|---|
| 绝对 mAP@0.5 | 0.5907（口径不同，不可直接比） | **0.5165** | — |
| **同一模型 500 张 vs 5000 张** | 0.4000（500 张） | **0.3668** | **高估 3.3 pt** |
| **INT8 掉点** | −1.76 pt | **−1.27 pt** | **高估 0.5 pt** |

> **"在 128 张上测"不只是"统计强度弱"，而是**系统性地夸大差异**。**
> **所以小数据集上的结论只能当"趋势"，不能当"数值"。**

#### ② INT8 的掉点很大一部分来自**低分框变多，而不是定位变差**

```
FP32  857,548 框
INT8  949,474 框     +10.7%（同一 conf=0.001 阈值）
```

**量化给分数引入噪声，把一批本该低于阈值的背景框推过了线 → 大量 FP → precision 下降 → 掉点。**

**佐证**：mAP50 掉 1.27 pt，但 **mAP75 只掉 1.17 pt** —— 如果是"定位变差"，更严格的阈值应该掉得更多；**实际是宽松阈值掉得更多，符合"多出低分误检"的解释。**

> **推论（未验证）**：实际部署用 `conf=0.25` 时，这个掉点可能观察不到。
> 要验证的话，需要在几个 conf 阈值上各测一次掉点曲线 —— **本项目没做，不当作结论。**

#### ③ 跨后端确认：**INT8 比 FP16 慢**，不是某个实现的偶然

| 后端 | 精度档 | 延迟 | INT8 相对 FP16 |
|---|---|---|---|
| **GPU / TensorRT** | FP16 | 2.10 ms | — |
| **GPU / TensorRT** | INT8 | **2.47 ms** | **慢 17.6%** |
| **CPU / onnxruntime** | FP16 | 61 ms/张 | — |
| **CPU / onnxruntime** | INT8 | **97 ms/张** | **慢 59%** |

**两个完全不同的后端、不同的量化实现（TRT 的 QDQ vs ORT 的 int8 kernel）、不同的访存层次，
都得到"INT8 比 FP16 慢"。**

> **这把正文"YOLOv8n 上 INT8 没有价值区间"这个结论从"一个后端上的观察"
> 抬到了"两个后端上的一致结论"** —— 而 CPU 上的差距更大（59% vs 17.6%），
> 说明这**不是某个后端的实现缺陷**，而是模型本身在 fp16 就已经不吃算力了。

**机理**：YOLOv8n 只有 3.2 M 参数、8.1 MB，**FP16 已经把它压到访存/派发受限区**；
INT8 再把权重减半收益很小，而**反量化（dequant）在每个算子边界都要付一次代价**——
在 CPU 上这个边界开销更贵（没有融合 kernel），所以差距更大。

### A.5 FP16 的结论要说得更准确

**FP16 与 FP32 的 mAP 差异（+0.02 pt）小于本次测量本身的粒度**：

- 一次评测集里"某张图有无检出"就能造成 ~0.02 pt 的波动（见 A.6）
- 所以正确表述是 **"FP16 在噪声范围内与 FP32 相同"**，而不是"FP16 比 FP32 高 0.02"

**这与正文里"FP16 上界掉点 < 1 pt"的论证一致，而且现在有实测了。**

**机理**：fp16 的最大有限值是 **65504**，而 YOLOv8n 的激活值远小于此 → 不发生钳位；
`convert_float_to_float16` 的 `max_finite_val=65504.0` 默认值正好匹配。

### A.6 一个必须披露的细节

**FP16 第一次跑的评测集是 4999 张，不是 5000。**

原因：脚本原来用 `{d["image_id"] for d in dets_out}` 当评测集 →
**某张图在 `conf=0.001` 下一个框都没出时，它被静默排除**，于是它的漏检不计入 FN，**mAP 偏高**。

**已修**（现在用"所有跑过推理的图"），并加了提示：

```
注意: N 张图在 conf=0.001 下无检出，仍计入评测（漏检计为 FN）
```

**影响量级**：1/5000 张 → **修复后复测 mAP@0.5 仍是 0.5167（变化 < 0.0001）**，**不影响任何结论**；
但它说明**"评测集"本身也是容易搞错的一环** —— 这和项目里"对比对象不一致"那一类问题是同源的。
